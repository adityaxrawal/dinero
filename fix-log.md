## TASK-DB-023: Implement Transaction Bounding for Background Writes (Prevent SQLITE_BUSY)

**Found:** Nothing existed — no `BatchWriter`, no bounded-transaction pattern anywhere in the ingestion/statement background tasks.

**What I did:** New `db/batch_writer.rs`. `BatchWriter` queues writes (each a boxed `Fn(&Connection) -> rusqlite::Result<()>`) and reports itself full once either bound is hit — `MAX_BATCH_ROWS = 20` or `MAX_BATCH_DURATION = 500ms` (Document 30's "max ~20 rows... max ~500ms"). `flush()` runs the whole queued batch inside one `BEGIN IMMEDIATE ... COMMIT` (via `rusqlite::Connection::transaction_with_behavior(Immediate)`), retrying the *entire* batch on `SQLITE_BUSY` with exponential backoff (50ms, 100ms, 200ms — `MAX_BUSY_RETRIES = 3`) before surfacing the error; any other error rolls back and returns immediately without retrying, since retrying a real constraint violation would just fail identically three more times. Deliberately synchronous (no `async`/`.await` anywhere in the type) so it's safe to call only from inside a `deadpool_sqlite::Connection::interact(...)` closure — the doc's "never holds a write transaction open across an `await` that could block on network I/O" is enforced by construction: there's no `await` in this file for a transaction to span.

**Verified:** `cargo build --lib` clean. 5 new tests: batch-full reporting at the row limit, no-op below the limit, a 3-write batch committing atomically, an empty flush being a true no-op, and a duplicate-primary-key write rolling back the *entire* batch (not just the failing row) rather than partially committing.
